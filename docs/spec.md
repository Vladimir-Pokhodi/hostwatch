# hostwatch: спецификация

Дата: 2026-11-07 · Тип: техника · Глубина: стандарт

## Идея одной фразой

Telegram-бот на своём VPS, который собирает серверы, балансы и нагрузку со всех хостеров владельца, предупреждает о проблемах, продлевает услуги с баланса хостера по правилу, заказывает серверы по кнопке и выставляет счета на пополнение по СБП или в крипте. Сам деньги с карт и кошельков не переводит.

Исходные документы: `docs/prompts/2026-11-07-hosting-monitor.md` (ТЗ), `docs/research.md` (разбор кабинетов), `docs/prompts/2026-11-07-hostwatch-grill.md` (что уже решено).

## Задача (фаза 1)

- **Проблема:** у владельца несколько серверов у разных хостеров. Он вручную обходит кабинеты и пропускает момент, когда кончаются деньги или падает сервер. Итог: внезапные отключения (например, VPN-нод с пользователями) и потерянное время.
- **Для кого:** один человек с 2–10 серверами у 2–5 хостеров: владельцы небольших VPN, ботов, pet-проектов. Чаще СНГ, СБП и крипта. Первая версия — **продукт для других**, а не только для автора: ставится на чистый VPS без своего домена.
- **Как решают сейчас:** вручную заходят в кабинеты, держат напоминания в календаре, автопродление и деньги на балансе с запасом.
- **Критерий успеха через месяц:**
  1. Ни одного отключения из-за неоплаты.
  2. В кабинеты хостеров владелец заходит только ради «войти заново», не чаще раза в неделю на хостера.
  3. Человек со стороны ставит бота по README на чистый VPS за 15 минут и подключает Aeza по ключу.
  4. Пятый хостер добавлен по инструкции без правок ядра.
- **Не входит:**
  - удаление серверов;
  - перевод денег с карты или криптокошелька (нет горячего кошелька, нет банковских API);
  - несколько пользователей в одной установке;
  - веб-интерфейс, кроме страницы входа;
  - проверка доступности серверов извне (ping, TCP, uptime). Порт SSH могут сменить, ping отключить, так что сигнал ненадёжный. hostwatch работает только с данными хостера.
- **Ограничения:** VPS 1 ядро / 2 ГБ / 30 ГБ: одновременно работает только один браузер (300–500 МБ). Стек Python, как в rw_bot. Пароли, 2FA и капчи вводит только человек.

### Изменения рамки относительно промта допроса

Пользователь расширил решённое:

- **Автооплата с баланса хостера по правилу.** Бот сам продлевает услугу или оплачивает счёт с баланса хостера за N дней до окончания, без кнопки. Работает только для отмеченных серверов, в пределах месячного лимита, с отчётом после каждого списания. Пополнение баланса по-прежнему делает человек по ссылке или QR.
- **Заказ новых серверов** по кнопке с подтверждением (хостер, тариф, локация, ОС, цена, период), запись в журнал. Нужен **во всех четырёх плагинах в v1**. Цена решения: отдельный этап разбора заказа у всех хостеров (у Regxa и AdminVPS это корзина WHMCS) и пробные заказы за реальные деньги (самый дешёвый тариф, удаление вручную).

## Рассмотренные подходы (фаза 2)

Почти вся архитектура задана заранее. Спорный и самый дорогой узел один: как человек входит на сайт хостера (Timeweb для счетов, Regxa, AdminVPS).

| Подход | Плюсы | Минусы | Цена | Обратимость |
|---|---|---|---|---|
| A. noVNC: Xvfb + Chromium + x11vnc + noVNC | Готовые компоненты, любой сайт и капча | Неудобно с телефона; виден весь рабочий стол, можно уйти на любой сайт; +150 МБ памяти | 1–2 дня | высокая |
| **B. Своя страница + трансляция Chromium через CDP** | Удобно на телефоне, одна вкладка, переходы только по домену хостера; тот же Chromium нужен для Cryptomus у Regxa | Свой код трансляции и ввода (~300–500 строк); перетаскивание в капчах надо проверить | 3–4 дня | средняя |
| C. Вставка cookie руками | Без инфраструктуры | Не сделать с телефона; сессия с IP человека (DDoS-Guard и QRATOR привязывают к IP); refresh-токен Timeweb сменится, когда человек откроет сайт | часы | высокая |
| D. Утилита входа на ПК | Нет веб-страницы на сервере | Нужен ПК с Python; та же проблема с IP | 1 день | высокая |

**Выбран B, C запасным путём для опытных.** Решающий довод: сессия создаётся с IP и отпечатком того же сервера, с которого бот потом ходит на сайт. B лучше A: ссылку открывают с телефона из Telegram, и мы сами решаем, куда можно перейти в браузере.

**Отвергнуты:** A — неудобно с телефона и слабый контроль. D — требует ПК, плохо для «продукта для других». Чистый C — не работает с телефона и ломается на привязке к IP.

## Решения (фаза 3)

1. **Где код** → отдельный git-репозиторий `D:\Projects\hostwatch`, публикуется на GitHub. На первом этапе туда переезжают `research.md`, `spec.md`, `plan.md` и промты этапов. Почему: `D:\Projects\vpn` не в git, и рядом лежат ключи VPN. Отвергнуто: папка в vpn — легко затащить лишнее в публичный репозиторий.
2. **Процессы и контейнеры** → три контейнера в Docker Compose:
   - `hostwatch` — один процесс asyncio: бот (aiogram 3), планировщик опроса, веб-сервер страницы входа (aiohttp), SQLite, секреты;
   - `browser` — официальный образ Playwright с `playwright run-server`. Chromium запускается только на время подключения, без дела контейнер занимает ~50 МБ. Нет доступа к базе и ключам. Версия Playwright совпадает с клиентской в `hostwatch`;
   - `caddy` — TLS и обратный прокси, наружу пускает только пути страницы входа.

   Почему: браузер, самый уязвимый компонент, изолирован от секретов, а память занята только во время входа. Отвергнуто: Chromium в основном контейнере (образ ~1,5 ГБ, браузер рядом с секретами); запуск контейнера браузера по требованию через Docker-сокет (сокет = root на хосте).

3. **Интерфейс плагина** →
   - Плагин — подпакет `hostwatch/plugins/<id>/` с классом-наследником `Plugin`. Ядро находит плагины, сканируя пакет; новый хостер = новая папка, ядро не меняется.
   - `meta: PluginMeta` — `id`, `name`, `site`, способ входа (`ApiKeyAuth(fields)` / `BrowserAuth(start_url, allowed_domains, cookies)` / несколько сразу, как у Timeweb), валюта.
   - Обязательные методы: `servers()`, `balance()`.
   - Возможности — `typing.Protocol`: `SupportsUsage`, `SupportsTopup`, `SupportsInvoices`, `SupportsPayInvoice`, `SupportsAutorenew`, `SupportsRenew`, `SupportsPower`, `SupportsOrder`. Реализовал методы — возможность есть. Отдельный список возможностей, который может разойтись с кодом, не нужен.
   - Второй уровень: `Server.actions` — что разрешено с этим сервером (у Aeza из `capabilities` услуги). Бот показывает кнопку, только если её разрешают и плагин, и сервер.
   - Секреты: ядро передаёт плагину `Secrets` аккаунта, плагин возвращает обновлённые (ротация refresh-токена Timeweb). Ядро сохраняет новые секреты **до** использования access-токена. На каждый аккаунт стоит `asyncio.Lock`, чтобы токен не прокрутили два запроса одновременно.
   - Ошибки плагина: `AuthExpired` → «надо войти заново»; `RateLimited` / `Blocked` → пауза опроса; `LayoutChanged` → «плагин устарел»; `HosterError(reason)` → показать причину. Ошибка одного плагина не трогает другие.
   - HTTP-клиент выдаёт ядро: таймауты, User-Agent как у браузера входа, прокси, без логирования тел и заголовков.
   - Несколько аккаунтов одного хостера: аккаунт = (плагин, подпись, секреты).
   - **Распространение:** плагины попадают в основной репозиторий через PR с ревью и тестами. Свой локальный плагин можно подключить через volume `plugins/` (подхватывается при старте). Почему: плагин видит сессии и деньги владельца, и непроверенный чужой код недопустим. Отвергнуто: отдельные pip-пакеты через entry points (непроверенный код, пересборка образа).
4. **Модель данных** (SQLite, одна база в `/data`):
   - `accounts` — id, plugin_id, подпись, статус подключения (`ok` / `relogin` / `error` / `disabled`), последняя ошибка, зашифрованные секреты;
   - `servers` — текущий снимок: account_id, внешний id, имя, тип (`vps` / `dedicated`), IP, тариф, статус (`running` / `stopped` / `suspended` / `unpaid` / `unknown`), цена и период, следующее списание или окончание, автопродление (`on` / `off` / `n/a`), модель оплаты (`hourly` / `periodic`), доступные действия, raw_status хостера;
   - `balance_history` — account_id, время, сумма, валюта. Отсюда считается реальный расход и видно пополнения;
   - `usage_cache` — последняя нагрузка по серверу с временем (истории нет: графики остаются у хостера);
   - `alerts` — ключ события (`balance_low:<acc>`, `status:<srv>` …), текущее значение, когда отправлено; нужен для защиты от повторов;
   - `journal` — каждое действие: кто (владелец / правило автооплаты), что, параметры, ответ хостера (без секретов), результат;
   - `payments` — созданные счета на пополнение: аккаунт, сумма, метод, ссылка, время, статус;
   - `settings` — язык, часовой пояс, пороги, тихие часы, время сводки, правила автооплаты.

   Деньги хранятся как `Money(amount: Decimal, currency: str)`, никаких float. `balance_history` и `journal` хранятся 180 дней.

5. **Секреты** → секреты аккаунтов лежат в SQLite и зашифрованы AES-GCM (`cryptography`). Ключ `HOSTWATCH_KEY` — в `.env` рядом с `docker-compose.yml`, вне тома `/data`, права 600. Бэкап `/data` без `.env` бесполезен.
   - **Модель угроз, честно.** Root на работающем сервере = доступ ко всему: ключ лежит в памяти процесса. Шифрование защищает только данные в покое (бэкап, снимок диска, база, по ошибке приложенная к issue). Ущерб от взлома больше баланса: сессия кабинета обычно позволяет сбросить root-пароль или открыть VNC любого сервера, а заказ — потратить баланс.
   - **Снижение ущерба** (это важнее шифрования):
     - README велит привязать API-ключ Aeza к IP бота;
     - у автооплаты и заказа есть месячный лимит в настройках; заказ дороже лимита требует второго подтверждения;
     - о каждом входе на страницу входа и каждом действии с деньгами приходит уведомление, отключить его нельзя;
     - в README есть раздел «Если сервер взломали»: где и как отозвать каждый ключ и сессию.
   - Отвергнуто: пароль при каждом старте — после ребута или обновления опрос и автооплата стоят, пока владелец не заметит, а это прямо бьёт по главному критерию успеха. Можно добавить опцией в v2.
6. **Ссылка входа** →
   - Адрес по умолчанию: `https://<IP сервера>/login/<токен>`, сертификат Let's Encrypt на IP. Такие выдаются с 15.01.2026, живут 6 дней, профиль `shortlived` ([анонс](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability)). Если задан `HOSTWATCH_DOMAIN` — используется домен. Для автора домен пока не нужен. IP сервера задаётся `HOSTWATCH_IP` в `.env`: по нему Caddy получает сертификат, а бот узнаёт свой сервер (решение 17); если пусто, бот спрашивает api.ipify.org.
   - Токен: 32 случайных байта, одноразовый. При первом открытии он сгорает, браузер получает cookie сессии входа, повторное открытие даёт 404. Открыть можно в течение 10 минут; сессия входа живёт 15 минут без действий. Одновременно идёт одна сессия входа.
   - При открытии бот присылает «Ссылку открыли: IP, браузер» с кнопкой «Это не я», которая убивает сессию.
   - Caddy отдаёт наружу только `/login/*`.
   - В Chromium разрешены только домены из `BrowserAuth.allowed_domains` и домены капч; остальное блокирует `page.route`.
   - Вход завершает плагин: проверяет успех (например, `GET /api/auth/session` у Regxa) и берёт только нужные cookie. Ядро закрывает контекст браузера и сообщает «Regxa подключена».
   - Запасной путь: команда `/cookie <аккаунт>` — вставить cookie руками.
   - Для README: hostwatch ставится на отдельный VPS, а не на VPN-ноду, потому что порты 80/443 там часто заняты Xray.
7. **Опрос** →
   - Статусы и нагрузка — раз в 15 мин ± 2 мин случайного сдвига; баланс и счета — раз в час. По кнопке «Обновить» опрос запускается сразу, но не чаще раза в минуту на аккаунт.
   - Ошибки: повтор через 15 → 30 → 60 → 120 мин. Уведомление — после 3 неудач подряд.
   - `AuthExpired`: опрос аккаунта останавливается, приходит одно уведомление с кнопкой «Войти заново».
   - `Blocked` / `RateLimited` (403, 429, страница DDoS-Guard): пауза 2 часа и уведомление.
   - У каждого аккаунта своя задача asyncio с таймаутом 60 с.
8. **Валюты** → суммы показываются в валюте хостера. Итоги «всего на балансах» и «всего в месяц» — в валюте владельца из настроек (по умолчанию RUB) с пометкой «≈, курс ЦБ на дату». Курс ЦБ РФ (`cbr.ru/scripts/XML_daily.asp`), запасной источник — `cbr-xml-daily.ru`, обновление раз в сутки. Если курса нет, итог показывается со старым курсом и датой или не показывается. Источник курса — маленький заменяемый модуль. Отвергнуто: ЕЦБ, у него нет рубля с 2022 года.
9. **Прогноз «денег хватит до»** (внутри аккаунта, в его валюте, без курсов). Бот всегда показывает, каким методом посчитано:
   - **Почасовая оплата** (Timeweb): берётся `hours_left` хостера, если он есть, иначе `баланс / сумма почасовых ставок`.
   - **Периодическая оплата** (Aeza, AdminVPS, Regxa): бот строит ленту будущих списаний (дата следующего списания + цена, дальше каждый период) по серверам, которые продлеваются (автопродление хостера или правило автооплаты бота), и идёт по ней, вычитая из баланса. «Хватит до» = дата первого списания, на которое денег уже нет. Пример ответа: «хватит до 23 ноября: 15.11 спишется €4.50 (beaver), 23.11 не хватит €12 на bear».
   - Серверы без продления в прогноз не входят и помечаются «не продлевается, закончится 30.11».
   - Сверка: реальный расход за 14 дней из `balance_history` (без пополнений). Если он расходится с прогнозом больше чем на 20 %, бот показывает оба числа.

10. **Автооплата** →
    - Если у хостера есть своё автопродление (Aeza `autoProlong`, AdminVPS HostingRenewals), бот только управляет им (вкл/выкл по кнопке) и следит, чтобы на балансе хватало денег. Сам не списывает.
    - Если своего нет (Regxa; WHMCS-счета AdminVPS, если кредит на них не применяется сам), бот по правилу оплачивает **уже выставленный хостером счёт** с баланса (`SupportsPayInvoice`), когда до срока осталось N дней (по умолчанию 3), и только для серверов с отметкой «автооплата». Новых счетов на продление бот не создаёт.
    - Защиты: месячный лимит на аккаунт; счёт оплачивается один раз (ID счёта в `journal`, проверка до вызова); перед оплатой бот перечитывает счёт и сверяет сумму. Если она выросла больше чем на 10 % от прошлого периода, бот не платит, а спрашивает. После каждого списания приходит отчёт.
    - Отвергнуто: бот сам продлевает всё, родное автопродление выключено. Если бот лежит в день продления, сервер отключат; к тому же риск двойного списания.
11. **Заказ сервера** (`SupportsOrder`, во всех четырёх плагинах в v1) →
    - Сценарий: «Заказать» → аккаунт → локация → тариф → ОС → период → итог с ценой → «Заказать за €4.50/мес?» Да / Отмена.
    - Каталог отдаёт `catalog()` плагина, кэш на час. Перед подтверждением цена перечитывается.
    - Оплата с баланса хостера. Не хватает — бот предлагает пополнить на недостающую сумму.
    - На карточке сервера есть кнопка «Заказать такой же» (тариф, локация, ОС скопированы).
    - Месячный лимит и второе подтверждение сверх лимита (решение 5). Запись в `journal`.
    - Доступ к новому серверу: публичный SSH-ключ владельца из настроек ставится при заказе, если хостер это умеет. Кнопка «Показать пароль»: бот запрашивает root-пароль у хостера (если тот его отдаёт), присылает его и удаляет сообщение через 5 минут. В базе пароль не хранится и в журнал не пишется.
    - Удаление серверов в бот не входит.

12. **Уведомления** (все пороги меняются в настройках):

    | Событие | Когда | Важность |
    |---|---|---|
    | Баланс кончится | прогноз < 5 дней; повтор при 2 и 1 дне | обычное; < 1 дня — критическое |
    | Статус сервера | стал `suspended` / `unpaid` / `stopped`, и это не действие владельца через бота | критическое |
    | Скоро окончание | за 3 дня, только если сервер не продлевается или на продление не хватит денег | обычное |
    | Нагрузка | CPU или RAM > 90 % три опроса подряд (~45 мин); диск > 90 % сразу | обычное |
    | Надо войти заново | сразу, один раз | обычное |
    | Плагин сломан | 3 неудачи подряд | обычное |
    | Действие с деньгами, открытие страницы входа | всегда | критическое |

    - Повторы: у события есть ключ (`balance_low:<acc>`) и состояние (`5d`, `2d`, `1d`). Бот пишет, когда состояние меняется или становится хуже. Пока критическое событие активно, напоминание раз в сутки. Когда событие ушло — сообщение «решено».
    - Часовой пояс выбирается при первом запуске (для RU предлагается Europe/Moscow, для EN — UTC).
    - Ежедневная сводка в 09:00.
    - Тихие часы 23:00–08:00: обычные события копятся и приходят одним сообщением в конце тихих часов, критические — сразу.
13. **i18n** → словари `hostwatch/locales/ru.py` и `en.py` и функция `t(key, **kwargs)`. Тест проверяет, что набор ключей в обоих языках совпадает. Язык выбирается при первом запуске и меняется в настройках. Сообщения плагинов об ошибках тоже идут через ключи. Отвергнуто: gettext/Babel — лишний шаг сборки ради двух языков.
14. **Тесты и CI** →
    - HTTP-клиент — `httpx`, в тестах ответы подменяет `respx`.
    - Записанные ответы сайтов лежат в `tests/fixtures/<plugin>/`. Записывает их команда `hostwatch record <аккаунт>`, она же прогоняет очистку: cookie, токены, email, имена и IP заменяются заглушками. Перед коммитом и в CI работает `gitleaks`.
    - Каждый плагин проходит общий контрактный тест (`tests/contract.py`): модели валидны, деньги в `Decimal`, возможности соответствуют методам, ошибки маппятся в типы ядра.
    - Вход через браузер проверяется e2e-тестом: в CI поднимается фальшивый сайт с формой входа, Playwright проходит вход через нашу страницу трансляции.
    - CI (GitHub Actions): `ruff`, `mypy --strict` на ядре, `pytest`, `gitleaks`, сборка образа. Живых хостеров CI не трогает.
    - Живая проверка вручную: `hostwatch check <аккаунт>` выводит серверы, баланс, возможности и время ответа, ничего не меняя.
15. **Развёртывание** →
    - Образ публикуется в GHCR по тегу релиза. `docker-compose.yml` и `.env.example` лежат в репозитории.
    - `install.sh` ставит Docker (если его нет), создаёт `/opt/hostwatch`, спрашивает `BOT_TOKEN` и `OWNER_ID`, генерирует `HOSTWATCH_KEY`, показывает его один раз с просьбой сохранить и запускает Compose. Больше в системе ничего не меняет (ни SSH, ни firewall).
    - Обновление: `cd /opt/hostwatch && docker compose pull && docker compose up -d`. Раз в сутки бот проверяет релизы на GitHub и пишет «вышла версия X» со ссылкой на changelog. Watchtower и Docker-сокет не используются.
    - Бэкап: каждую ночь `sqlite3 .backup` в `/data/backups`, хранится 7 штук. Кнопка «Прислать бэкап» в настройках отправляет файл в Telegram. Секреты в нём зашифрованы, ключа там нет.
    - Логи: в stdout, у Docker ротация `json-file` 10 МБ × 3. Тела запросов и заголовки не пишутся. Фильтр логов заменяет на `***` все значения из секретов аккаунтов, которые сейчас загружены.
    - Прокси для Telegram: необязательный `TG_PROXY`, как в rw_bot.
16. **Сторонний хостер** →
    - `docs/adding-a-hoster.md`: как разбирать кабинет (API → XHR → HTML), что записать про каждый запрос, как записать фикстуры, чек-лист перед PR.
    - `hostwatch new-plugin <id>` создаёт папку плагина из шаблона, файл тестов и пустые фикстуры.
    - Плагин принимается, когда он проходит контрактный тест и `check` на живом аккаунте (вывод `check` приложен к PR, без личных данных).

17. **Сторож следит за собой** → бот находит свой сервер среди серверов аккаунтов (по публичному IP), помечает «это hostwatch» и предупреждает о его балансе на 3 дня раньше. Необязательный `HEARTBEAT_URL` в `.env` (например, healthchecks.io): пинг каждые 5 минут, так что о молчании бота сообщит внешний сервис. В README: «не пришла утренняя сводка — бот лежит».
18. **Этапы** → 15 этапов, в работу бот выходит после этапа 05 (Aeza и Timeweb по API, уведомления, деплой). Подробно — `docs/plan.md`.

## Сценарии бота

Все апдейты не от `OWNER_ID` молча отбрасываются (middleware до любых хендлеров).

- **Первый запуск** (`/start`): язык → часовой пояс → валюта итогов → «Подключите первого хостера» → экран «Подключить».
- **Главное меню:** Сводка · Серверы · Баланс · Интеграции · Заказать · Журнал · Настройки. `/menu` открывает его из любого места.
- **Навигация:** на каждом экране «⬅️ Назад» на уровень выше и «🏠 Меню»; у разделов главного меню только «🏠 Меню». Кнопки редактируют то же сообщение, а не шлют новое.
- **Сводка:** по каждому аккаунту баланс, «хватит до», число серверов по статусам, проблемы. Внизу итоги в валюте владельца. Аккаунт с ошибкой показывается строкой «AdminVPS: не удалось получить данные (причина), данные от 07.11 14:30».
- **Серверы:** сначала аккаунты хостеров с числом серверов и значком ⚠ при проблемах; дальше серверы аккаунта, VPS и дедики отдельно, по 8 на страницу; «Назад» с карточки ведёт к странице этого сервера. Карточка сервера: имя, IP, тариф, статус, цена, следующее списание, автопродление, нагрузка (или «хостер не отдаёт нагрузку»), время данных. Кнопки — только поддерживаемые плагином и сервером: Питание (вкл / выкл / перезагрузка), Автопродление, Продлить, Автооплата, Заказать такой же, Показать пароль, Обновить.
- **Баланс → Пополнить:** способ (СБП / крипта → сеть) → сумма. Варианты: минимум хостера, «чтобы хватило до конца следующего месяца», своя сумма. Бот создаёт счёт и присылает ссылку (для СБП по возможности `qr.nspk.ru`), QR-картинку и кнопку «Оплатил». После «Оплатил» перечитывает баланс через 2, 5 и 10 минут и сообщает результат. Если счёт через запросы создать нельзя, присылает ссылку на страницу пополнения.
- **Интеграции:** только подключённые аккаунты со статусом «подключено / надо войти заново / ошибка / отключено» и кнопка «+ Подключить». Она открывает экран «Подключить»: по кнопке на каждого ещё не подключённого хостера и «+ ещё аккаунт …» для подключённых. Карточка аккаунта: последний успешный опрос, ошибка, кнопки «Войти заново» / «Изменить ключ» / «Отключить» / «Удалить». Добавление: хостер → подпись → ввод ключа (сообщение с ключом бот сразу удаляет) или ссылка входа.
- **Ссылка входа** (из бота и из `hostwatch login`) приходит отдельным сообщением. Оно и «Ссылку открыли…» удаляются, когда вход завершён, отменён, закрыт, ссылка истекла (10 минут без открытия) или её заменила новая. Сообщения старше 48 часов Telegram удалять не даёт: их бот правит на «Ссылка больше не действует».
- **Заказать:** сценарий из решения 11.
- **Журнал:** последние 20 действий: кто (владелец / правило), что, результат. Можно листать.
- **Настройки:** язык, часовой пояс, валюта итогов, пороги и тихие часы, время сводки, лимиты автооплаты и заказа, SSH-ключ, «Прислать бэкап».
- **Подтверждения:** любое действие из управления, оплаты и заказа показывает «что, где, сколько» и кнопки «Да / Отмена». В callback лежит одноразовый nonce, живущий 5 минут; повторное нажатие игнорируется. Результат и ответ хостера (без секретов) пишутся в `journal`.

## Требования к коду и текстам

- Код как у профессионала: понятная структура, типы (`mypy --strict` на ядре), маленькие функции, имена, по которым ясно, что происходит. Комментарии только там, где без них непонятно *почему*. Без лишних абстракций и «на всякий случай».
- Модели — pydantic v2 или dataclasses. Ответы хостеров разбираются строгими моделями: незнакомое поле или статус → `LayoutChanged` или `unknown`, а не угаданное значение.
- Деньги — только `Decimal` в `Money`.
- Документация для людей: простые предложения, конкретика, команды, которые можно скопировать. Без признаков сгенерированного текста (https://ru.wikipedia.org/wiki/Википедия:Признаки_сгенерированности_текста): никаких «важно отметить», «в современном мире», цепочек из трёх прилагательных, пафоса, пустых вступлений и выводов. README на английском, рядом `README.ru.md`.
- Секреты, токены, cookie и пароли не попадают в git, логи, журнал и тексты ошибок.
- Лицензия MIT.

«Бот всегда живой и сам предупредит». hostwatch стоит у Aeza и оплачивается с того же баланса, за которым следит. Молчание бота выглядит как «всё хорошо». Закрыто решением 17.

### Критерии остановки
